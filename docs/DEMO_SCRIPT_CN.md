# Site Inspection AI 演示操作手册与演讲稿

生产环境：<https://site-inspection-ai.vercel.app>

GitHub：<https://github.com/HAMILTON0044/site-inspection-ai>

本文分为两部分：

1. **从零初始化系统**：从账号注册开始，建立 Manager、巡检员和演示项目。
2. **比赛现场演示**：控制在 5–7 分钟，可直接照着操作和讲解。

---

## 一、演示目标

演示结束时，评委应该理解以下完整闭环：

```text
注册与登录
  → Manager 创建项目并添加巡检员
  → 巡检员上传现场照片
  → 浏览器本地 YOLO 识别
  → LLM 根据结构化检测结果和备注生成 finding 草稿
  → 巡检员人工修改、批准或驳回
  → 正式提交到私有云端空间
  → Manager 指派整改任务
  → 巡检员提交整改证据
  → Manager 复核关闭或重新打开
  → PDF 报告与审计记录长期留存
```

本项目不是让 AI 直接代替安全负责人下结论，而是让 AI 完成重复的信息整理工作，并保留人工审核、照片证据和完整审计链路。

## 二、演示前准备

### 2.1 准备三个邮箱账号

建议准备三个真实可收邮件的邮箱，分别作为：

| 账号 | 角色 | 用途 |
| --- | --- | --- |
| Demo Manager | Manager | 创建项目、添加成员、指派和复核 finding |
| Inspector A | 巡检员 | 上传原始巡检照片并提交正式记录 |
| Inspector B | 巡检员 | 接收整改任务并上传整改证据 |

密码不要写入 GitHub、演示文档或聊天记录。建议使用临时强密码，并保存在密码管理器中。

### 2.2 准备演示照片

至少准备：

- 2 张清晰的施工现场照片，画面中尽量包含人员、安全帽、反光背心等 PPE 目标。
- 1 张整改后的照片，用于 Inspector B 上传跟进证据。
- 单张照片建议小于 3 MB，避免现场网络过慢。

当前 YOLO 模型主要识别 PPE。为了保证演示稳定，优先选择主体清晰、光线正常、人员不太小的照片。

### 2.3 浏览器安排

为了减少反复退出登录，建议使用三个独立浏览器会话：

- Chrome：Manager
- Edge：Inspector A
- 无痕窗口或其他浏览器：Inspector B

正式演示前统一设置为 100% 缩放，并关闭密码、邮箱和无关标签页，避免泄露个人信息。

### 2.4 演示前检查清单

- [ ] 生产网站能够打开。
- [ ] LLM 网关额度正常。
- [ ] Supabase 项目状态正常。
- [ ] 三个邮箱能够接收验证邮件。
- [ ] 演示图片已经放在容易找到的文件夹中。
- [ ] 已经完整彩排一次，总时长不超过 7 分钟。
- [ ] 预先保留一份生成成功的 PDF，作为网络异常时的备用材料。

## 三、从零初始化系统

本节假设生产网站和 Supabase 数据库已经部署，但还没有演示账号、项目和业务记录。

### 3.1 注册 Manager 候选账号

1. 打开 <https://site-inspection-ai.vercel.app/login>。
2. 在“姓名”中填写，例如：`演示项目经理`。
3. 输入 Manager 候选邮箱和至少 8 位密码。
4. 点击 **注册巡检员**。
5. 如果页面提示检查邮箱，打开验证邮件并完成确认。
6. 回到登录页，用该账号登录一次，确认账号有效，然后退出。

安全规则：所有新注册账号默认都是 `INSPECTOR`，前端不能自行升级为 Manager。

### 3.2 在 Supabase 中升级 Manager

1. 打开 Supabase Dashboard。
2. 进入项目 `site-inspection-ai`。
3. 打开 **Authentication → Users**，确认 Manager 候选邮箱已经存在。
4. 打开 **SQL Editor → New query**。
5. 先执行查询，确认目标账号：

```sql
select id, email, display_name, role, is_active
from public.profiles
where lower(email) = lower('manager@example.com');
```

6. 把示例邮箱替换为真实邮箱，确认无误后执行升级：

```sql
update public.profiles
set role = 'MANAGER',
    is_active = true
where lower(email) = lower('manager@example.com')
returning id, email, display_name, role, is_active;
```

7. 确认返回结果为 `role = MANAGER`。
8. 让 Manager 退出并重新登录。

不要修改 `auth.users` metadata 来设置角色。当前应用读取的是 `public.profiles.role`。

### 3.3 注册两个巡检员

分别使用 Inspector A 和 Inspector B 的邮箱执行：

1. 填写姓名、邮箱和密码。
2. 点击 **注册巡检员**。
3. 完成邮箱验证。
4. 登录后确认侧边栏可以看到“新建智能巡检”“巡检记录”“问题看板”“团队与项目”和“报告中心”。

### 3.4 Manager 创建项目

1. Manager 登录。
2. 进入 **团队与项目**。
3. 在“创建施工项目”中填写：
   - 项目名称：`滨江商务中心二期`
   - 项目编号：`DEMO-BJC-2026`
   - 项目说明：`用于施工现场安全巡检和整改闭环演示`
4. 点击 **创建项目**。
5. 在项目详情页找到“巡检员成员”。
6. 输入 Inspector A 的注册邮箱，点击 **添加成员**。
7. 输入 Inspector B 的注册邮箱，再次点击 **添加成员**。
8. 确认两名巡检员都显示在成员列表中。

项目是当前系统的数据权限边界。巡检员只能读取自己参与项目中的正式记录。

## 四、完整业务操作流程

### 4.1 Inspector A 创建巡检

1. Inspector A 登录。
2. 打开 **新建智能巡检**。
3. 点击 **选择文件**，选择 2–3 张现场照片。
4. 点击 **识别全部照片**。
5. 等待每张照片显示检测框和检测数量。
6. 点击不同照片，展示检测框会跟随当前照片切换。
7. 如果发现明显误检，可以取消对应检测结果的勾选。

建议使用的巡检备注：

```text
地下车库施工区域，重点检查现场人员的安全帽、反光背心和其他个人防护用品佩戴情况。
```

8. 点击 **开始分析**。

### 4.2 人工审核 AI finding

分析完成后：

1. 展示 AI 生成的 finding 标题、风险、描述、建议措施和证据照片。
2. 点击 finding 中的证据照片，展示页面跳转到对应照片并高亮检测框。
3. 修改一条 finding 的文字，说明 AI 结果可以被人工纠正。
4. 点击 **批准** 保留有效 finding。
5. 对明显不合理的草稿点击 **驳回**。
6. 确认所有 finding 均已批准或驳回，不能留下“待审核”状态。

这里要强调：AI 输出只是草稿，最终安全结论由巡检员确认。

### 4.3 正式提交并生成 PDF

1. 在“所属项目”选择 `滨江商务中心二期`。
2. 点击 **提交到云端**。
3. 等待“正式提交成功”提示。
4. 点击 **下载正式 PDF 报告**。此时系统不仅会把 PDF 下载到本机，也会将报告归档到当前巡检记录。
5. 简单展示 PDF 中的：
   - 巡检摘要
   - 已批准 finding
   - 证据照片
   - YOLO 检测框
   - AI 辅助生成免责声明
   - 巡检员和 Manager 签字区
6. 打开 **巡检记录**，进入刚提交的记录详情。
7. 展示正式照片、检测框、finding、事件时间线和报告归档信息。

> 注意：如果在正式提交前点击下载，系统仍可以生成本地 PDF，但这份 PDF 尚未关联云端巡检记录，因此不会出现在报告中心。现场演示时应按“先提交、后下载”的顺序操作。

正式提交后，照片进入 Supabase 私有 Storage，业务数据通过数据库事务保存。其他未加入项目的巡检员不能读取这些内容。

### 4.4 Manager 指派整改

1. 切换到 Manager 浏览器。
2. 打开 **问题看板**。
3. 点击刚生成的开放问题。
4. 在“指派与风险设置”中：
   - 负责人选择 Inspector B
   - 设置整改期限
   - 风险等级选择“高风险”或“中风险”
   - 填写调整说明
5. 点击 **保存管理设置**。

### 4.5 Inspector B 提交整改证据

1. 切换到 Inspector B。
2. 打开 **问题看板**，选择“分配给我的问题”。
3. 进入 finding 详情，点击 **开始整改**。
4. 在“添加整改跟进”中填写：

```text
已补发并检查个人防护用品，现场人员已按要求佩戴，提交复核。
```

5. 上传整改后的照片。
6. 勾选 **同时提交 Manager 复核**。
7. 点击 **保存整改跟进**。

### 4.6 Manager 复核关闭或重开

1. 切回 Manager。
2. 打开等待复核的 finding。
3. 填写复核结论。
4. 根据演示需要选择：
   - **复核通过并关闭**；或
   - **复核不通过，重新打开**。
5. 展示审计时间线中的指派、整改、提交复核、关闭或重开事件。
6. 打开 **报告中心**，展示已归档的正式 PDF。

到这里，完整闭环结束。

比赛现场不建议临时注册三个账号和等待三封验证邮件。推荐提前完成第三章的账号与项目初始化，现场只简要说明注册和 Manager 提权机制。

| 时间 | 操作 | 要表达的重点 |
| --- | --- | --- |
| 0:00–0:40 | 展示登录页 | 问题背景和产品定位 |
| 0:40–1:10 | 展示项目和角色 | Manager/Inspector 权限边界 |
| 1:10–2:10 | 上传照片并运行 YOLO | 图片在浏览器本地识别 |

## 六、可直接照读的演讲稿

### 6.1 开场（约 40 秒）

> 各位好，我们的项目叫 Site Inspection AI。施工现场巡检人员每天需要拍摄大量照片、记录观察结果，再手工整理成正式报告。这个过程重复、耗时，而且照片、问题、整改措施经常分散在不同工具里，导致信息传递和整改跟进不够及时。
>
> 我们希望解决的并不是“让 AI 代替安全负责人”，而是让 AI 自动完成照片识别、问题草稿和报告整理，同时把最终判断保留给人工，让每一次现场巡检都有证据可追溯。

### 6.2 账号、权限和项目（约 30 秒）

> 系统分为巡检员和 Manager 两种角色。新注册账号固定为巡检员，不能自行提升权限。Manager 必须由受信任的项目管理员授权。
>
> Manager 可以创建项目并添加巡检员。项目同时也是数据访问边界，巡检员只能看到自己参与项目中的正式记录。

### 6.3 本地视觉识别（约 60 秒）

> 现在我以巡检员身份上传几张施工现场照片。系统使用 YOLOv8 ONNX 模型直接在浏览器里识别安全帽、反光背心等目标，并在照片上绘制检测框。
>
> 这里有一个关键的隐私设计：原始照片不会发送给当前 LLM 网关。LLM 接收到的是按照片分组的结构化检测结果和巡检备注。这样既减少图片传输，也能保留每条结论对应的照片证据。

### 6.4 AI finding 与人工审核（约 60 秒）

> 点击开始分析后，AI 会生成 finding 草稿，包括问题标题、风险等级、问题说明、建议措施和证据照片。
>
> 但系统不会直接把 AI 结论当成正式安全结论。巡检员可以修改内容、排除误检，并逐条批准或驳回。只要内容被修改，审核状态就会重新变为待确认。
>
> 点击证据照片，页面会跳转到原图并高亮对应检测框，因此每一条问题都可以追溯到具体照片和检测结果。

### 6.5 报告和正式归档（约 50 秒）

> 审核完成后，系统可以生成正式 PDF 报告。报告包含巡检摘要、批准的问题、证据照片、检测框、建议措施和签字区域。
>
> 正式提交时，照片保存到 Supabase 私有 Storage，问题和证据关系通过数据库事务写入。系统同时使用行级权限控制，避免无关用户读取其他项目的数据。

### 6.6 整改闭环（约 50 秒）

> 提交后的问题会进入团队问题看板。Manager 可以设置风险等级、整改期限，并把问题指派给具体巡检员。
>
> 被指派的巡检员可以上传整改说明和新照片，再提交 Manager 复核。Manager 可以关闭问题，也可以复核不通过并重新打开。整个过程采用只追加的审计记录，不会覆盖原始巡检报告。

### 6.7 技术架构（约 30 秒）

> 前端使用 Next.js 和 React，并部署在 Vercel。浏览器端通过 ONNX Runtime 运行 YOLOv8。Supabase 提供账号认证、PostgreSQL、私有文件存储和行级权限控制。黑客松指定的 LLM 负责根据结构化检测结果生成问题草稿。
>
> 这个架构把视觉识别、语言模型、人工审核、团队协作和正式报告组合成了一个可运行的轻量巡检 Agent。

### 6.8 后续提升（约 35 秒）

> 当前版本已经完成了从照片识别到整改关闭的最小闭环。后续可以从四个方向继续提升。
>
> 第一，使用更多真实施工数据训练专用视觉模型，让系统能够更可靠地识别通道堵塞、电缆未固定和材料堆放等场景。第二，增加移动端和离线巡检能力，适应地下室或网络较差的工地。第三，加入消息通知、整改 SLA 和项目统计看板。第四，与 BIM、企业 SSO 或现有工程管理平台集成。
>
> 如果未来使用支持图像输入的合规模型，也可以在保留隐私和人工审核的前提下增加多模态复核，但不会取消现有的证据链和人工确认机制。

### 6.9 结束语（约 15 秒）

> Site Inspection AI 的核心价值，是减少巡检后的重复整理工作，让问题、证据、责任人和整改结果进入同一个闭环。谢谢大家。

## 七、常见问题回答

### 7.1 AI 会不会误判？

会。因此当前系统把 AI 输出定义为草稿，必须由巡检员批准或驳回后才能进入正式记录。每条 finding 都保留证据照片和检测框。

### 7.2 为什么不用 LLM 直接看图片？

当前黑客松指定网关不提供稳定的图像输入能力，因此使用浏览器端 YOLO 提取结构化视觉证据，再交给 LLM 整理问题。这样也减少了把现场照片传给外部模型的需求。

### 7.3 数据安全吗？

正式照片存放在 Supabase 私有 Bucket 中，数据库启用了 Row Level Security。巡检草稿只允许创建者访问；提交后的记录按项目成员关系授权。

### 7.4 这是通用 Agent 吗？

当前是面向施工巡检场景的专用工作流 Agent。它能够组织视觉识别、LLM 草拟、人工审核、云端归档和整改状态机，但没有为了概念复杂度而提前引入 LangChain、向量数据库或多 Agent 系统。

### 7.5 为什么使用 YOLOv8n？

YOLOv8n 模型体积较小，能够在浏览器端运行，适合黑客松原型和现场快速响应。当前模型主要用于 PPE 识别，未来会通过施工领域数据继续训练和评估。

## 八、现场故障备用方案

### LLM 网关暂时不可用

- 不要反复点击。
- 说明视觉识别已经在本地完成，当前失败属于外部 LLM 服务。
- 切换到预先保存的本地巡检历史或已经提交的正式记录。
- 展示预先生成的 PDF。

### 邮箱验证邮件延迟

- 正式比赛前提前创建并验证账号。
- 不要把现场时间浪费在等待邮件上。
- 必要时在 Supabase Authentication 页面确认用户状态。

### YOLO 首次加载较慢

- 首次访问需要下载约 12.2 MB 的 ONNX 模型。
- 提前打开工作台，让浏览器完成模型缓存。
- 演示只选择 1–2 张清晰照片。

### 图片检测效果不理想

- 切换到提前测试过的备用照片。
- 主动说明当前模型主要覆盖 PPE，不要声称它已经可靠识别所有施工风险。

### 账号切换耗时

- 使用不同浏览器分别保持 Manager、Inspector A 和 Inspector B 登录。
- 如果时间不足，只演示 Inspector A 提交和 Manager 看板，其余流程用已经存在的审计记录说明。
